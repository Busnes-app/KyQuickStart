# Phase 4: Edge and proxy implementation

The operator chooses endpoints when running the installer; no personal domains or live
infrastructure are prerequisites for building it. Implement and test locally.

## Sequence

1. Resolve frp shared-443 SNI routing and client-IP preservation against primary sources
   and a disposable runnable test. Record evidence in the sibling frp research spec.
2. Add a secret-free edge schema to `stack.yaml`: one edge per target, one hostname owner,
   selected Cloudflare/frp connection, NPM API endpoint and routes with certificate IDs.
   Reject unsafe proxy trust, invalid upstreams, exposed admin ports and incompatible placement.
3. Implement NPM API reconciliation: refuse foreign hostname ownership; create disabled;
   verify desired configuration; enable and prove NPM accepted it. Preserve other hosts and
   never touch its database. Sanitize forwarded headers in a full per-host location.
4. Wire edge reconciliation into `apply` under existing target locks, add read-only
   `verify-edge`, and read credentials only from protected target files or owned Kubernetes
   Secrets. API redirects and remote error bodies cannot expose credentials.
5. Deploy pinned connector containers with file-backed tokens, and verify routes and the
   product's forwarded-header report. Existing tunnel/server infrastructure can be reused.
6. Add fresh NPM bootstrap and DNS-01 certificate issuance, Cloudflare API provisioning and
   managed frps deployment. Retain restricted Kubernetes policy; validate upstream NPM launch
   compatibility before choosing a deployment layout.
7. Run `make ci`, existing e2e, and disposable edge integration tests. Update DOX and operating
   documentation; leave an explicit readiness record for unimplemented gates.

## Acceptance

- A second apply is a no-op; a partial create resumes from live state.
- Foreign hosts and unrelated NPM configuration are unchanged.
- No credentials enter stack.yaml, command arguments, step hashes, logs or state files.
- Spoofed forwarding headers do not become the product's client address or scheme.
- frp preserves client IP and TLS ciphertext through the public server.
- Public connection paths cannot reach NPM administration.
- Docker and Kubernetes deployment support is verified separately; neither is inferred.

## Dependencies

Product G11 supplies the status endpoint and trusted-proxy configuration for full verification.
Identity and suite product setup remain gated by tagged, tested `apply-setup` capabilities.
This phase plan does not declare those gates open.
